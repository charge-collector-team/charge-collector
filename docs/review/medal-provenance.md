# 검토 제안: 교환 이력과 현재 보유 출처의 구분

**상태: 설계 검토 문서만 추가 / 앱 코드·데이터 변경 없음.** 디자인 PR과 분리한 기술 검토다. 현재 앱이 잘못됐다고 단정하거나 보유 출처 추적이 구현됐다고 표시하지 않는다.

## 현재 확인한 동작

- `GameState.owned`는 메달별 현재 총수량이다.
- `acquisitions`는 CHARGE / TRADE / SYNTHESIS별 과거 획득 기록이다.
- `acceptTrade`는 총수량을 줄이거나 늘리고, 받은 메달의 TRADE 획득 기록을 추가한다. 보낸 메달의 출처를 기록하지 않는다.
- `synthesize`는 같은 도안 동 10개를 줄이고 은 1개를 늘린다. 어떤 출처의 동을 사용했는지는 기록하지 않는다.
- `Showcase`의 교환 필터와 상세의 받은 경로는 과거 획득 기록을 기준으로 한다.
- 친구 데이터는 메달별 총수량뿐이며 친구의 획득 출처를 제공하지 않는다.

## 이 검토가 필요한 이유

같은 메달을 직접 1개·교환으로 1개 얻은 뒤 1개를 보내면 현재 총수량은 1개다. 과거 TRADE 기록은 남지만, 남아 있는 1개가 어떤 출처인지 현재 데이터만으로는 알 수 없다. 합성으로 동을 사용한 경우에도 같은 문제가 생긴다.

따라서 다음 두 표시를 구분해야 한다.

| 표시 의미 | 현재 정확하게 표시 가능한가 | 필요한 작업 |
|---|---|---|
| 이 메달을 교환으로 받은 기록이 있음 (`교환 이력`) | 가능 | 기존 획득 기록으로 UI 라벨 도출 |
| 현재 보유분에 교환으로 받은 메달이 남아 있음 (`교환 포함`) | 불가능 | 출처별 재고 및 출고/소모 기록 보완 |

권장 1차안은 `교환 이력`이다. 이것을 선택하면 엔진의 재고 정책을 바꿀 필요가 없다. 라벨 UI 시안은 디자인 PR에서 검토하고, 이 브랜치에는 넣지 않는다.

## 개발팀 결정 항목

- [ ] 첫 버전의 라벨 의미를 과거 이력으로 둘지, 현재 보유 출처로 둘지 결정
- [ ] 현재 보유 출처가 필요하면 교환 예약·출고·합성에서 어떤 출처를 잠그고 소모하는지 결정
- [ ] 구형 데이터의 출처를 추정하지 않고 미확인 상태로 보존하는 방법 결정
- [ ] 친구의 출처 데이터가 없을 때 표시를 생략하는 범위 확인
- [ ] 엔진 보완이 필요할 때만 별도 구현 브랜치/PR로 진행

출처별 보유량을 선택하면 수량 보존, 잠금·취소·만료, 합성, 데이터 이전에 대한 테스트가 필요하다. 이 문서에서는 FIFO나 특정 출처 우선 소모를 임의로 확정하지 않는다.
